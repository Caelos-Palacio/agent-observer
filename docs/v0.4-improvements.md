# Observer 0.4: privacidad, cobertura y rendimiento

## Cambios

El almacén usa identidades aleatorias por instancia. La tabla de correspondencias vive solo en memoria, está limitada a2048entradas y nunca se guarda; al alcanzar el límite falla sin ampliar memoria. Una nueva instancia no vincula automáticamente IDs predecibles anteriores. Los datos históricos con IDs SHA256 de16hex siguen siendo legibles; `identityMode:'legacy-sha256'` es una opción explícita de compatibilidad. No elimina la correlación que ya exista en archivos antiguos ni protege frente a procesos maliciosos del mismo UID.

Los nombres de herramientas se comparan con `DEFAULT_TOOLS` o una lista `registeredTools` de hasta256nombres que suministra el anfitrión confiable. Los identificadores desconocidos válidos se sustituyen por `other`; no se guardan nombres arbitrarios proporcionados por un evento. Los IDs de protocolo ya opacos (`eventId`, `requestId`, `producerId`) deben proceder del anfitrión; validar su forma no detecta un productor malicioso que codifique datos en ellos.

Pi emite metadatos v2 con IDs aleatorios, secuencia, hora de captura `occurredAt`/`observedAt` y un mismo `requestId` para inicio y fin de herramienta. No lee el cuerpo de llamadas/mensajes. Los nombres de workers no se guardan ni se derivan para formar su identidad. La comunicación entre sesiones de otro proyecto no se captura automáticamente.

El estado de captura diferencia `droppedEvents` conocidos, `unconfirmedEvents` (lotes con error/timeout cuyo estado real en disco puede ser parcial), correlaciones expulsadas de la caché de100entradas y cola pendiente. La revisión puede consultar lo retenido aunque la captura se haya desactivado. Estos contadores son del proceso actual, no un historial durable de todos los reinicios; no garantizan captura completa.

`reviewVersion:2`, `guideVersion` y `ruleVersion` identifican la interpretación. Cada hallazgo añade tamaño observado de muestra, llamadas, ventana y truncamiento conocido. La guía de umbrales v1 sigue siendo compatible. No se ejecutan recomendaciones automáticamente.

## Recuperación explícita de JSONL

```sh
node src/cli.mjs recover --directory /ruta/privada/logs
```

Los locks nuevos son directorios no vacíos `.writer-lock.d`, publicados mediante rename atómico desde un candidato preparado con un archivo de propietario cuyo nombre incluye PID y token aleatorio. Todos los escritores, lectores y recuperadores de esta versión usan el mismo protocolo. Un directorio vivo no vacío no puede ser reemplazado por otro rename POSIX; al liberar/recuperar solo se elimina el nombre único validado, nunca el de un escritor nuevo. Se probaron las carreras de dos recuperadores y de liberación seguida de un nuevo escritor con barreras deterministas. La recuperación solo retira un lock privado y válido cuando el sistema confirma que su PID ya no existe. Rechaza procesos vivos, errores de permisos, cualquier `.writer.lock` antiguo o contenido inverificable; si un PID fue reutilizado por un proceso vivo, se niega conservadoramente. No usa tiempos máximos para suponer que un escritor murió. Los candidatos de un proceso que murió antes de publicar requieren inspección manual; después de32candidatos residuales se rechazan nuevas adquisiciones sin borrado automático. Los locks verificados requieren Linux/POSIX en un filesystem local: este protocolo no se validó en Windows ni en filesystem de red. Antes de actualizar hay que detener/reiniciar todos los procesos con el escritor anterior; mezclar versiones que no comparten el protocolo no está soportado.

Tras adquirir su propio lock, verifica los registros completos del archivo actual y elimina únicamente una cola incompleta de hasta2KiB, dentro del archivo acotado a1MiB, sincronizando el truncado. No repara JSON corrupto en líneas terminadas ni archivos fuera de límites; nunca imprime fragmentos. Los eventos completos se conservan. No ejecutamos este comando sobre registros reales durante las pruebas.

No se añadió otro SQLite ni daemon para Pi: Node22 ofrece SQLite experimental y su API síncrona necesitaría otro diseño para evitar bloquear el anfitrión. El recuperador más batching resuelve los fallos acotados actuales conservando formato y dependencias. JSONL sigue sin ser una transacción ni prometer durabilidad tras pérdida de energía; una escritura/lote fallido puede ser parcial. Los importadores Codex/broker mantienen SQLite `DELETE`/`FULL`.

## Evaluación reproducible

```sh
npm test
npm run evaluate
npm run benchmark
node scripts/smoke-broker-integration.mjs /ruta/agent-credential-broker
```

El corpus v1 tiene12casos operacionales etiquetados:4hallazgos esperados,0falsos positivos y0falsos negativos en esta versión. Incluye éxitos, agentes/sesiones distintos, cancelaciones, denegaciones, intención, incertidumbre, ausencia de contadores y presupuestos. Precisión/recall1.0 valen únicamente para este corpus pequeño; no estiman precisión real ni calidad semántica del trabajo.

El benchmark usa200llamadas/400eventos ficticios, vacía cada25llamadas y ejecuta3procesos aislados por modalidad. La referencia es el almacén de commit `92b2b60` con los hooks actuales: elimina campos v2 que no conocía, por lo que mide un formato más pequeño. No es una comparación de privacidad o capacidad equivalente. Reporta tiempo total, CPU, p50/p95 del par de hooks, pico RSS, bytes y descartes. La modalidad desactivada produce cero eventos; incluye coste del bucle de prueba.

Resultado de una ejecución local en Linux, Node22.22.2 (medianas de3repeticiones):

| Métrica | Referencia sin batch | Nuevo batch |
|---|---:|---:|
| Tiempo total400eventos |233.4ms|55.9ms|
| CPU del ensayo |273.5ms|70.8ms|
| p95 par de hooks |0.0725ms|0.0488ms|
| Pico RSS incluido runtime |83.0MiB|83.5MiB|
| Bytes/evento |164.5|449.2|
| Eventos descartados |0|0|

La mejora medida justificó lotes de hasta25eventos en Pi: se adquiere un lock y abre el archivo por lote, conservando orden y rotación, sin subproceso por evento. El SDK admite hasta100eventos por batch y valida todo el lote antes de escribir. Más correlación cuesta aproximadamente2.7veces más bytes por evento en este ensayo, aunque se mantienen límites de disco. No se bajó la durabilidad del broker ni se activó WAL. Estos tiempos dependen del equipo, caché y carga; no son garantías para producción.

## Broker v2 y garantías

La importación admite v1 de7campos y v2 de12campos. V2 añade `executionId`, `sequence`, `producerId`, `occurredAtUTC`, `observedAtUTC`; todas las propiedades son obligatorias y cerradas por versión. Se conservan como metadatos tipados, nunca como autorización. La base v1 se valida con su esquema exacto antes de una migración transaccional al esquema de almacenamiento2; las consultas de bases antiguas siguen siendo de solo lectura.

`executionId` permite correlacionar etapas cuando el productor comparte su ID; `producerId` y secuencia permiten contar huecos solamente entre secuencias observadas retenidas. Cero huecos no demuestra historia completa ni integridad. Los IDs/timestamps no autentican un exportado; `authenticatedAudit:false` sigue explícito. No hay checkpoint con firma externa ni se afirma evidencia inalterable.

La deduplicación conserva la primera proyección de cada evento: si ya importaste el mismo ID en v1, reimportarlo como v2 no inventa/añade retrospectivamente metadatos. Para analizar íntegramente un exportado v2 ya importado como v1, selecciona una base nueva explícita. Los datos antiguos no reciben fechas/identidades falsas. Sesión/principal del broker siguen no disponibles; `executionId` no identifica a un agente.

Fuentes de diseño: [OpenTelemetry: datos sensibles](https://opentelemetry.io/docs/security/handling-sensitive-data/), [modelo de logs](https://opentelemetry.io/docs/specs/otel/logs/data-model/), [rendimiento y memoria](https://opentelemetry.io/docs/specs/otel/performance/), [transacciones SQLite](https://www.sqlite.org/atomiccommit.html). Aplicar sus semánticas no requiere instalar un Collector ni exportar datos a servicios externos.

### Actualización de procesos existentes

1. Cierra de forma normal todos los procesos Pi/Observer que estén escribiendo en ese directorio; conserva sus sesiones de trabajo antes de cerrarlos. No mezcles escritores anteriores con esta versión ni al volver a una anterior.
2. Conserva una copia privada del directorio de logs. Si hay un `.writer.lock` heredado, inspecciónalo y confirma que ningún escritor anterior sigue activo. La aplicación se niega a retirarlo automáticamente, aunque esté vacío.
3. Solo después de esa comprobación humana, aparta el archivo heredado para conservarlo como evidencia de inspección. Por ejemplo, usando una ruta explícita propia:

   ```sh
   observer_dir=/ruta/privada/logs
   mv -- "$observer_dir/.writer.lock" "$observer_dir/.writer.lock.reviewed"
   ```

4. Inicia los nuevos procesos. `recover --directory DIR` solo recupera propietarios nuevos cuyo PID el sistema demuestra ausente y colas incompletas acotadas; no fuerza la migración de procesos vivos.

Estos pasos no se ejecutaron en registros reales del usuario. Un PID reutilizado vivo o un lock inverificable requiere inspección, nunca borrado forzado por edad. El puente Node del broker admite hasta8MiB de salida y la proyección Python limita sus eventos a7MiB; una regresión importa y lee10000eventos v2 completos, sin reducir la ventana para esconder desbordamientos.
