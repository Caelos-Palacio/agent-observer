# Observer 0.4: privacy, coverage and performance

> Spanish original: [es/v0.4-improvements.md](es/v0.4-improvements.md)

## Changes

The store uses random per-instance identities. The correspondence table lives only in memory, is limited to 2048 entries and is never saved; on reaching the limit it fails instead of growing memory. A new instance does not automatically link earlier predictable IDs. Historical data with 16-hex SHA256 IDs remains readable; `identityMode:'legacy-sha256'` is an explicit compatibility option. It does not remove correlation already present in old files and does not protect against malicious processes of the same UID.

Tool names are compared with `DEFAULT_TOOLS` or a `registeredTools` list of up to 256 names supplied by the trusted host. Valid unknown identifiers are replaced by `other`; arbitrary names supplied by an event are not stored. Already-opaque protocol IDs (`eventId`, `requestId`, `producerId`) must come from the host; validating their shape does not detect a malicious producer that encodes data in them.

Pi emits v2 metadata with random IDs, a sequence, capture times `occurredAt`/`observedAt` and the same `requestId` for the start and end of a tool call. It does not read the body of calls/messages. Worker names are neither stored nor used to derive their identity. Communication between sessions of another project is not captured automatically.

Capture state distinguishes known `droppedEvents`, `unconfirmedEvents` (batches with an error/timeout whose real state on disk may be partial), correlations evicted from the 100-entry cache and the pending queue. Review can query what was retained even if capture has been disabled. These counters belong to the current process, not a durable history across all restarts; they do not guarantee complete capture.

`reviewVersion:2`, `guideVersion` and `ruleVersion` identify the interpretation. Each finding adds the observed sample size, calls, window and known truncation. The v1 threshold guide remains compatible. No recommendation is executed automatically.

## Explicit JSONL recovery

```sh
node src/cli.mjs recover --directory /private/path/logs
```

New locks are non-empty `.writer-lock.d` directories, published through an atomic rename from a prepared candidate holding an owner file whose name includes the PID and a random token. All writers, readers and recoverers of this version use the same protocol. A live non-empty directory cannot be replaced by another POSIX rename; on release/recovery only the validated unique name is removed, never that of a new writer. The races between two recoverers and between a release followed by a new writer were tested with deterministic barriers. Recovery only removes a private, valid lock when the system confirms its PID no longer exists. It rejects live processes, permission errors, any old `.writer.lock` or unverifiable content; if a PID was reused by a live process, it conservatively refuses. It uses no maximum ages to assume a writer died. Candidates of a process that died before publishing need manual inspection; after 32 leftover candidates new acquisitions are rejected without automatic deletion. Verified locks require Linux/POSIX on a local filesystem: this protocol was not validated on Windows or network filesystems. Before upgrading, stop/restart all processes running the previous writer; mixing versions that do not share the protocol is unsupported.

After acquiring its own lock, it verifies the complete records of the current file and removes only an incomplete tail of up to 2 KiB, inside the file bounded to 1 MiB, syncing the truncation. It does not repair corrupt JSON in terminated lines or files outside limits; it never prints fragments. Complete events are preserved. We did not run this command on real logs during testing.

No second SQLite store or daemon was added for Pi: Node 22 offers experimental SQLite and its synchronous API would need another design to avoid blocking the host. The recoverer plus batching solves the current bounded failures while keeping the format and dependencies. JSONL is still not a transaction and promises no durability after power loss; a failed write/batch may be partial. The Codex/broker importers keep SQLite `DELETE`/`FULL`.

## Reproducible evaluation

```sh
npm test
npm run evaluate
npm run benchmark
node scripts/smoke-broker-integration.mjs /path/to/agent-credential-broker
```

Corpus v1 has 12 labelled operational cases: 4 expected findings, 0 false positives and 0 false negatives in this version. It includes successes, different agents/sessions, cancellations, denials, intent, uncertainty, missing counters and budgets. Precision/recall of 1.0 hold only for this small corpus; they do not estimate real precision or the semantic quality of the work.

The benchmark uses 200 fictitious calls/400 events, flushes every 25 calls and runs 3 isolated processes per mode. The reference is the store at commit `92b2b60` with the current hooks: it drops v2 fields it did not know, so it measures a smaller format. It is not a comparison of privacy or equivalent capability. It reports total time, CPU, p50/p95 of the hook pair, peak RSS, bytes and drops. The disabled mode produces zero events; it includes the cost of the test loop.

Result of one local run on Linux, Node 22.22.2 (medians of 3 repetitions):

| Metric | Reference without batching | New batching |
|---|---:|---:|
| Total time, 400 events | 233.4 ms | 55.9 ms |
| Trial CPU | 273.5 ms | 70.8 ms |
| p95 hook pair | 0.0725 ms | 0.0488 ms |
| Peak RSS including runtime | 83.0 MiB | 83.5 MiB |
| Bytes/event | 164.5 | 449.2 |
| Dropped events | 0 | 0 |

The measured improvement justified batches of up to 25 events in Pi: one lock is acquired and the file opened per batch, preserving order and rotation, with no subprocess per event. The SDK accepts up to 100 events per batch and validates the whole batch before writing. More correlation costs roughly 2.7 times more bytes per event in this trial, although disk limits are kept. The broker's durability was not lowered and WAL was not enabled. These times depend on the machine, cache and load; they are not production guarantees.

## Broker v2 and guarantees

The import accepts 7-field v1 and 12-field v2. V2 adds `executionId`, `sequence`, `producerId`, `occurredAtUTC`, `observedAtUTC`; all properties are mandatory and closed per version. They are kept as typed metadata, never as authorization. The v1 database is validated against its exact schema before a transactional migration to storage schema 2; queries against old databases remain read-only.

`executionId` allows correlating stages when the producer shares its ID; `producerId` and the sequence allow counting gaps only among retained observed sequences. Zero gaps does not prove complete history or integrity. IDs/timestamps do not authenticate an export; `authenticatedAudit:false` stays explicit. There is no checkpoint with an external signature and no tamper-proof evidence is claimed.

Deduplication keeps the first projection of each event: if you already imported the same ID as v1, re-importing it as v2 does not retroactively invent/add metadata. To fully analyze a v2 export already imported as v1, choose an explicit new database. Old data does not receive false dates/identities. The broker's session/principal remain unavailable; `executionId` does not identify an agent.

Design sources: [OpenTelemetry: sensitive data](https://opentelemetry.io/docs/security/handling-sensitive-data/), [logs data model](https://opentelemetry.io/docs/specs/otel/logs/data-model/), [performance and memory](https://opentelemetry.io/docs/specs/otel/performance/), [SQLite transactions](https://www.sqlite.org/atomiccommit.html). Applying their semantics does not require installing a Collector or exporting data to external services.

### Upgrading existing processes

1. Close normally all Pi/Observer processes that are writing to that directory; save their work sessions before closing them. Do not mix earlier writers with this version, nor when going back to an earlier one.
2. Keep a private copy of the log directory. If there is a legacy `.writer.lock`, inspect it and confirm that no earlier writer is still active. The application refuses to remove it automatically, even if it is empty.
3. Only after that human check, set the legacy file aside to keep it as inspection evidence. For example, using your own explicit path:

   ```sh
   observer_dir=/private/path/logs
   mv -- "$observer_dir/.writer.lock" "$observer_dir/.writer.lock.reviewed"
   ```

4. Start the new processes. `recover --directory DIR` only recovers new owners whose PID the system proves absent and bounded incomplete tails; it does not force migration of live processes.

These steps were not run on any real user logs. A live reused PID or an unverifiable lock needs inspection, never forced deletion by age. The broker's Node bridge accepts up to 8 MiB of output and the Python projection limits its events to 7 MiB; a regression imports and reads 10000 complete v2 events, without shrinking the window to hide overflows.
